# github-archiver: Gerrit plugin

In-process port of the Python archiver. Same design, same guarantees, running
inside Gerrit instead of beside it.

**Status: complete and building, never yet run inside a Gerrit.** 49 tests
pass against the real 3.14.3 API and `mvn package` produces a loadable jar,
but nothing has exercised it against a live server. Treat the first
deployment as the real test.

## Why in-process

Three things the external service could not do cleanly:

**Secrets.** The GitHub token lives in `$site/etc/secure.config` under
`[plugin "github-archiver"]`. Gerrit's injected server config wraps the
`SecureStore` (`GerritServerConfigProvider`), so `PluginConfigFactory
.getFromGerritConfig(name, true).getString("githubToken")` resolves it and
picks up rotations without a restart. One credential store instead of two.

**Scheduling.** The sweep uses `ScheduleConfig`, the same mechanism core
Gerrit uses for `gc`, `changeCleanup` and the attention set. No cron, no
second container.

**No webhook authentication hack.** The `webhooks` plugin can neither sign
payloads nor send custom headers, which forced a credential into a URL
against a receiver whose `sslVerify` defaults to false. In-process listeners
delete that whole problem.

The cost, stated plainly: this runs in Gerrit's JVM. An archiver bug degrades
the review server. Every listener must hand off to the work queue rather than
block on GitHub, and the sweep must stay bounded.

## Configuration

`$site/etc/github-archiver.config`:

```ini
[github]
	apiUrl = https://api.github.com

[archiver]
	skipAutogenerated = true
	skipPrivate = true

[sweep]
	lookbackMinutes = 180
	limit = 500

[project "myproject"]
	owner = TheoGoudout
	repo = myproject
	branchPrefix = gerrit-archive
	branch = master        ; repeatable; all branches when absent
```

`$site/etc/secure.config`:

```ini
[plugin "github-archiver"]
	githubToken = ghp_...
```

## Build

Maven, not Bazel: `gerrit-plugin-api` is on Maven Central, so this builds
without a Gerrit source tree or bazlets.

```bash
mvn -q package
cp target/github-archiver-0.1.0.jar $site/plugins/
```

Pin `gerrit.version` in `pom.xml` to the Gerrit you run. The api dependency is
`provided`: every class it carries is already on Gerrit's classpath, and
bundling them would produce a 67MB jar with a second copy of Guice, JGit and
Guava inside the server.

## Running it

```bash
mvn -q package
cp target/github-archiver-0.1.0.jar $site/plugins/
ssh -p 29418 host gerrit plugin reload github-archiver
```

Then, on demand:

```bash
ssh -p 29418 host github-archiver sweep          # lookback window
ssh -p 29418 host github-archiver sweep --full   # everything, for cutover
```

## The sweep is the correctness mechanism

Not the listeners. A listener can be missed: a plugin reload, a projection
that threw, the queue shedding load under a burst. So the sweep re-derives
state from Gerrit and converges GitHub, and the listeners only shorten the
delay.

**Set `sweep.interval`.** Without it the plugin logs a warning and runs on
events alone, where a missed event is lost for good.

Listeners hand a change id to the queue and return — no Gerrit call, no GitHub
call, no I/O. They run on Gerrit's own threads, and blocking one on a GitHub
round trip would stall the review server. That is the central hazard of
running in-process, and the enqueue-and-return rule is what contains it.

## What is not verified

The plugin has never been loaded into a running Gerrit. Compilation against
the real API and 49 passing tests rule out a large class of mistakes, but not
Guice wiring errors, request-context problems under a background thread, or
anything about how JGit authenticates to GitHub from inside the server. Deploy
it somewhere disposable first.

## Notes on the port

No mirror. The external archiver had to clone each project and fetch to get
patch set commits; in-process they are already in the repository
`GitRepositoryManager` hands over, so `JGitOps` pushes straight from it.

Comments are fetched with `commentsRequest().withContext(true)`, the typed
equivalent of the `enable-context` request parameter. The Python client
silently omitted that parameter for a while, which left every unanchorable
comment quoting nothing. Here it is a method on a builder rather than a string
that can be forgotten.

## Storage

`Ledger` deliberately avoids an embedded database. The plugin API bundles
none, and taking a dependency to hold a few thousand rows is heavier than the
problem. Appends are flushed on write; a crash loses at most the record in
flight, and that case is already covered by the provenance markers, which let
the projector re-adopt anything GitHub accepted but the ledger missed.

`Projection` uses the typed `ChangeInfo` / `CommentInfo` / `ChangeMessageInfo`
rather than parsed JSON, which removes a class of field-name mistakes the
Python version could only catch at runtime.
